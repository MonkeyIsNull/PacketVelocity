# PacketVelocity benchmarks

Real, measured numbers for PacketVelocity's **offline processing pipeline** -
everything that happens to a packet *after* it has been captured: **filter ->
flow tracking -> output**. Produced by `make bench` (source:
[`bench/bench_pipeline.c`](bench/bench_pipeline.c)).

> **These are OFFLINE processing-pipeline numbers, not live capture off the
> wire.** Live capture needs root and a real NIC and is deliberately **out of
> scope** here. See the caveats at the bottom.

## Results (Apple M1, macOS, arm64)

| field | value |
|-------|-------|
| CPU | Apple M1 (`MacBookPro17,1`), 8 logical cores |
| Memory | 16 GB |
| OS / kernel | macOS, Darwin 24.6.0 (arm64) |
| Compiler | Apple clang 17.0.0, `-O3 -std=gnu11` |
| Packet set | 2,000,000 synthetic frames held in memory (generation **not** timed) |
| Packet mix | ~75% IPv4 / ~25% IPv6; ~70% TCP / ~30% UDP; on-wire sizes 64–1514 B (bimodal: mostly small acks + bulk), mean **610 B/pkt**, total **1.16 GiB** |
| Distinct flows | 20,000 unique 5-tuples |
| Filter | `(or (= proto 6) (= ip-version 6))` — IPv4 TCP **or** any IPv6; accepts **77.9%** (1,557,298 pkts) |
| Timing | `clock_gettime(CLOCK_MONOTONIC)`, 2 warmup + 7 timed runs, best + median reported |

## What each row includes

Each stage is the previous one **plus one more piece**, so the cost localises.
The in-memory replay loop mirrors the real capture callback in
[`src/pcv_main.c`](src/pcv_main.c) / [`tests/test_replay.c`](tests/test_replay.c).

- **a. baseline** — the replay loop visiting all 2M packet descriptors and
  touching one byte of each frame. This is the overhead floor (array walk +
  memory touch); everything else is measured on top of it.
- **b. + filter** — `pcv_filter_apply()` running the compiled VFM/VFLisp program
  above (JIT-compiled) on **every** packet.
- **c. + flow tracking** — accepted packets additionally fed to
  `pcv_flow_update_v6()` (the IPv4/IPv6 5-tuple aggregator): hash insert /
  lookup, per-packet accounting, and a periodic expiry sweep that evicts idle
  flows (2 s idle timeout, swept every 8192 packets). Both the v4 and v6 paths
  run because the filter admits both. The flow table is allocated/freed outside
  the timed region.
- **d. + stdout (format)** — accepted packets additionally formatted into the
  tcpdump-style line (`inet_ntop` ×2, `strftime`, two `snprintf`s) and written
  to a **discarded fd** (`/dev/null` `FILE*`), so the formatting + stdio cost is
  measured without a real terminal. The per-packet `getifaddrs()` direction
  lookup the live path does is intentionally omitted (there is no NIC offline).
- **d. + ristretto (per-pkt)** — accepted packets additionally appended as **one
  RistrettoDB V2 row per packet** to a **temp `.rdb` file**, so real
  `mmap`/`msync`/disk I/O is honestly included. The timed region covers the
  append loop **and** the final durable flush + close; the file is truncated
  before each run and deleted afterwards. (RISTRETTO=1 only.)
- **d. + ristretto (per-flow)** — accepted packets fed to the per-flow sink,
  which **fuses flow tracking and emission**, writing **one row per flow** to a
  temp `.rdb` file. Rows are emitted on eviction and, for still-open flows, at
  shutdown — so the timed region includes the sink's `destroy` (flush every open
  flow + durable sync). (RISTRETTO=1 only.)

## How to run

```bash
# Default (hermetic) build: stages a–c + stdout. Links ZERO RistrettoDB symbols.
make bench

# All six stages (adds both RistrettoDB V2 sinks). Needs ../RistrettoDB built.
make bench RISTRETTO=1

# Tiny-N smoke run (no perf meaning) — used by CI to prove the bench compiles
# and runs in both build modes without imposing any perf threshold.
make bench BENCH_QUICK=1
make bench RISTRETTO=1 BENCH_QUICK=1
```

The packet count and flow count can be overridden at run time without
recompiling, e.g. `PCV_BENCH_PACKETS=4000000 PCV_BENCH_FLOWS=50000 ./bench/bench_pipeline`.
The generator is seeded, so a given (packets, flows) pair is reproducible.

## Observations / things that surprised us

- **stdout formatting is the slowest sink.** Rendering the tcpdump-style text
  line (`inet_ntop` + `strftime` + `snprintf`) costs *more* per accepted packet
  (~1025 ns) than appending a fixed-width binary row to the mmap-backed
  RistrettoDB per-packet table (~918 ns), temp-file fsync included. Text
  formatting, not disk I/O, dominates here.
- **Per-flow output is ~2.5× faster than per-packet** (357 vs 918 ns/pkt),
  because it writes ~20,000 flow rows instead of ~1.56M packet rows — the win is
  proportional to the packet-to-flow fan-in of the traffic.
- **VFM arm64-JIT does not implement L4 port fields.** VFLisp compiles
  `src-port` / `dst-port` to the `VFM_IPV6_EXT` opcode, whose `default` case in
  `VelocityFilterMachine/src/jit_arm64.c` emits a stub returning `-1` (DROP)
  rather than falling back to the interpreter. So a port-based filter such as
  `(= dst-port 443)` matches **zero** packets under the default JIT on Apple
  Silicon. The `proto` field is also IPv4-only (fixed offset), so `(= proto 6)`
  never matches IPv6. We therefore benchmark with the JIT-safe dual-stack filter
  `(or (= proto 6) (= ip-version 6))`. This is a VFM finding, outside the scope
  of this benchmark, but worth recording.

## Caveats

1. **Offline, post-capture only.** These measure the processing pipeline
   (filter → flow → output) over an in-memory packet set. They are **not** a
   live-capture-off-the-wire measurement — no BPF/AF_PACKET, no kernel, no NIC,
   no interrupts, no copy from the capture ring. Live capture needs root + real
   hardware and is out of scope.
2. **This specific CPU.** The numbers reflect one Apple M1. Treat them as a
   ballpark and, above all, as a **relative comparison between stages** — not a
   throughput guarantee for other hardware. Re-run `make bench` on your box.
3. **Linux / live-hardware numbers are still TODO.** They need a Linux host with
   a real NIC and root. The bench is confirmed to *compile and run* on
   glibc/Linux (CI builds it in both modes), but no Linux perf numbers are
   published here, and **no Docker/QEMU-emulated numbers** are ever reported —
   emulated throughput is meaningless.
